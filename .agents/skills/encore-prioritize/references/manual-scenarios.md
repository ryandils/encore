# Manual review scenarios

These scenarios describe expected skill behavior. They do not assert that a live GitHub exercise or an automated test ran. Use synthetic issue labels such as A/B below rather than treating any Encore issue number as permanently preferred.

| Scenario | Evidence supplied | Expected recommendation and boundaries |
| --- | --- | --- |
| Bare invocation | User sends only `$encore-prioritize`; current inventory is accessible. | Default to Encore and the current build plan, gather evidence without a routine clarification, and give a short justified recommendation rather than dumping every issue. |
| High priority, blocked | A has the strongest product impact or explicit priority, but prerequisite B has an unmerged PR. C is ready and unclaimed. | Explain A's importance and named blocker; rank C among work eligible now. Do not call A ready from its label or begin it on B's unmerged branch. |
| Stale implementation issue | A is open/Ready, local checkout lacks its code, and verified current `main` contains merged code/tests covering acceptance. | Identify A as already implemented from current-main evidence; do not rank it as new work or edit/close its issue. If acceptance is only partly covered, identify the precise outstanding scope. |
| Closed as not planned | A is closed/not-planned although its body still says Ready and code is absent. | Treat A as historical evidence, not ready work. Explain that reconsidering its scope needs explicit authorization; do not reopen or recommend immediate implementation from stale body status. |
| Claimed work under the same account | A has no assignee, but its comments/body record another chat's branch and active claim under the current account; or an open PR covers A. | Treat A as owned/in review and exclude duplicate implementation. Do not erase the claim or assume the shared account authorizes takeover. |
| Incomplete API evidence | Issue enumeration is truncated, comments cannot be retrieved, or dependency merge status is unavailable. | Report the observed gap and safe access failure details through the inventory workflow. Give only provisional advice on verified facts; do not claim the global highest priority or infer unclaimed status from missing data. |
| Valuable parent milestone | A tracking parent unlocks several features but contains multiple child deliverables with mixed prerequisites. | Explain unlock value and assess an eligible child; do not present the entire parent as a small ready task. |
| Parallel work request | A and B appear independent, but both rely on an unmerged shared schema; C has merged prerequisites and no overlap. | Recommend only verified ready implementation such as C. Offer read-only preparation for A/B; do not create competing foundations. |
| No ready deliverable | Every inspected implementation issue is blocked, owned, or already implemented and coverage is adequate. | State that none is ready, identify the best unblock/review/preparation opportunity, and make no claim or file change. |
| Focused user goal | User prioritizes rapid pilot-risk reduction over cosmetic polish; ready A improves a verified correctness boundary while ready B is cosmetic. | Explain the judgment favoring A, cite relevant acceptance and risk evidence, label effort estimates, and acknowledge any competing declared priority or build-plan conflict. |
| Recommendation accepted conversationally | User says the recommendation makes sense without asking for implementation. | Keep the outcome as advice. Do not treat agreement as authorization to claim/code; explicit implementation authorization is required for orchestrator handoff and a fresh readiness check. |
| Recommendation and implementation requested together | User explicitly asks to recommend the best ready issue and implement it. | Complete the read-only recommendation, then transfer the chosen authorized scope to encore-orchestrator for a fresh readiness/ownership check. Do not demand an extra authorization turn or perform writes inside prioritization. |

For every scenario, verify that facts and opinion are distinguishable, source freshness and limitations are visible, and no issue/Git/code writes or dependency installations occur.
